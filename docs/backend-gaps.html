What Is Now Integrated
Frontend work completed in the latest sprint — these screens now call real API endpoints.
✅
All items below are wired. The CMS still falls back to localStorage when the API is unreachable, so the UI remains usable during development without a backend.

CMS: Idea form submission (public site)

IdeaFormModal.jsx — registers citizen / civil servant, fetches the active form, maps fields by template_key, and submits answers with file upload support.

CMS: Login

Login.jsx — The two-step UI (email → 6-digit code boxes) is unchanged. In the code-verify step, the joined digits are posted as the password to POST /api/auth/login. On success the token is stored as otci.cms_token in localStorage.

POST/api/auth/loginBody: { email, password } — token stored as otci.cms_token
⚠️
UI mismatch remains: The login screen labels the second field "6-digit code" and says "We sent a code to your email." In reality users must type their password into those six boxes. Update the UI copy or add an OTP send/verify endpoint (see §4.1).

CMS: Gallery / Media library

Media.jsx — The gallery list loads from the API on mount and falls back to seed data on error. All mutations are now wired:

GET/api/admin/galleryLoad folder list on mount
POST/api/admin/galleryCreate new folder
PUT/api/admin/gallery/:idDebounced title / description update (800 ms)
PATCH/api/admin/gallery/:id/visibilityToggle folder visibility
DELETE/api/admin/gallery/:idDelete folder
POST/api/admin/gallery/:id/imagesMultipart image upload; falls back to base64 on error
DELETE/api/admin/gallery/:id/images/:imageIdRemove individual image

CMS: Editor — publish, section save, section toggle

Editor.jsx — Three previously mocked actions now call real endpoints:

POST/api/admin/pages/:slug/publishPublish page — local state updated after API call
PATCH/api/admin/pages/:slug/sections/:uidToggle section visibility ({ visible: bool })
PUT/api/admin/pages/:slug/sections/:uidAuto-save section content — debounced 1500 ms

CMS: Admins (wired in a prior sprint)

Admins.jsx — Full CRUD: list admins, invite (single + batch), deactivate, reactivate, resend invite, revoke invite. App.jsx logout calls POST /api/v1/admin/logout.

CMS: Overview dashboard

Overview.jsx — Calls the dashboard endpoint on mount. API-sourced counts for sections, media, and pages replace local store computations; falls back gracefully when unreachable. Recent activity in the timeline is sourced from recent_activity[] in the response.

GET/api/admin/dashboardMounted once; response extracted from body.dashboard

The frontend maps the following fields from body.dashboard:

{
  "dashboard": {
    "sections":        { "total": 48, "live": 41, "hidden": 7 },
    "media":           { "images": 134, "folders": 8, "visible_folders": 6, "empty_folders": 1 },
    "pages":           { "published": 7, "changes": 2, "in_review": 1 },
    "recent_activity": [
      {
        "actor":        "Babatunde Fashola",
        "action":       "page_published",
        "action_label": "Published page",
        "subject":      "About",
        "page":         "about",
        "created_at":   "2026-11-08T14:22:00Z"
      }
    ]
  }
}
⚠️
Response key is body.dashboard, not body.data. The standard cmsApi.call() helper returns body.data ?? body and would silently miss the dashboard key. The endpoint is therefore called with cmsApiFetch directly and the key is extracted manually.

CMS: Activity log

Activity.jsx — Fetches the last 100 activity entries on mount and replaces S.activity with live data. Falls back to the existing local store (seeded demo entries) if the request fails.

GET/api/admin/activityQuery: ?per_page=100 — response key is body.activity[]

Each activity item is mapped to the Timeline shape. The fields the frontend reads are:

{
  "activity": [
    {
      "actor":        "Babatunde Fashola",
      "action":       "page_published",
      "action_label": "Published page",
      "subject":      "About",
      "page":         "about",
      "created_at":   "2026-11-08T14:22:00Z"
    }
  ],
  "meta": { "current_page": 1, "per_page": 100, "total": 342, "last_page": 4 }
}

action values that do not map directly to Timeline verb keys are translated via a VERB_MAP: sent_for_review → "sent for review", withdrew_review → "discarded", reordered → "edited", uploaded → "uploaded to", removed → "deleted". Unmapped values fall back to action_label then action.

⚠️
Response key is body.activity, not body.data. Same extraction issue as the dashboard; called with cmsApiFetch directly.

CMS: Charters list

Charters.jsx — Loads charters from the API on mount. Charters that have been edited locally (flagged _dirty or _fresh) are preserved and not overwritten by the API response. The API counts for services, fee tables, and issues replace the previously computed empty-array lengths.

GET/api/admin/chartersResponse key is body.charters[]

Fields the frontend reads from each charter item:

{
  "charters": [
    {
      "key":             "mof-001",
      "id":              12,
      "name":            "Ministry of Finance Charter",
      "short":           "MoF",
      "sector":          "Finance",
      "icon":            "gov",
      "state":           "published",
      "issues_count":    0,
      "services_count":  8,
      "fee_tables_count": 3
    }
  ],
  "meta": { "current_page": 1, "per_page": 50, "total": 17, "last_page": 1 }
}

state maps to the local status: "published" → status: 'published'; "changes" → status: 'published' + _dirty: true; "coming" → status: 'coming'; anything else → 'draft'.

Charter CRUD (create, update, delete, publish, PDF upload) remains local-only. See §4.4 for the remaining work.

OTCI Public Site — Missing & Mismatched Endpoints
The public website at otci.lagosstate.gov.ng. Idea submission is wired; four categories below remain static.

A. Newsletter subscription

The site footer contains a newsletter sign-up form (#ftNews) that collects an email address and shows a success message. Currently the form validates client-side and shows success without calling any backend. No endpoint exists.

POST/api/v1/public/newsletter/subscribe

Request body (JSON):

{
  "email": "ada@example.com"
}

Expected response:

{
  "success": true,
  "message": "You're subscribed. The next briefing will land in your inbox."
}
ℹ️
Always return 200 OK regardless of whether the email already exists, to prevent enumeration. If using a third-party email platform (Mailchimp, Brevo, etc.), this endpoint can be a thin proxy.

B. Citizen / MDA feedback submission

A floating "Share feedback" button (FeedbackFab) and a "Share feedback" link in the footer both trigger a feedback modal. The modal collects feedback but has no backend endpoint to send it to.

POST/api/v1/public/feedback

Request body (JSON):

{
  "email": "ada@example.com",    // optional — not required for anonymous feedback
  "message": "The permit process took 6 weeks...",
  "type": "mda"                  // "general" | "mda" (optional, defaults to "general")
}

Expected response:

{
  "success": true,
  "message": "Thank you for your feedback.",
  "data": {
    "reference_code": "FBK-2026-0042"
  }
}

C. Contact / Management Consulting Services form

The Management Consulting Services department page and the footer link to #ms/contact, which opens a contact request form. No backend endpoint exists.

E–K. Registration & submission spec mismatches

The following items are gaps between the existing API spec and the registration/submission flow as implemented in the frontend. Each requires a decision or confirmation from the backend team.

  • E
    LASRRA ID type missing from means_of_id_type enum The registration form asks users to upload their LASRRA ID. The API's means_of_id_type enum is national_id | passport | drivers_license | voters_card. LASRRA is not listed. The frontend currently sends national_id as a fallback.

    Action needed: Either add lasrra to the enum, or confirm that national_id is the correct mapping for LASRRA cards.
  • F
    Oracle payroll number not in civil servant registration The civil servant payload has account_officer_email, account_officer_role, designation, and grade_level, but no payroll/oracle number.

    Action needed: Confirm whether Oracle number is required. If yes, add oracle_number?: string to the civil servant registration endpoint.
  • G
    date_of_birth required but absent from spec examples Action needed: Confirm the accepted format is YYYY-MM-DD. Add a saved example to the Postman collection.
  • H
    account_officer_role vs. the civil servant's own designation Action needed: Clarify whether account_officer_role is the supervisor's job title or the registrant's own designation.
  • I
    Idea form is now authentication-required — confirm no anonymous path needed The API requires the user to be registered and authenticated before submitting. The frontend implements a combined register-then-submit flow.

    Action needed: Confirm with the product team that there is no anonymous submission path required.
  • J
    Media upload response shape not documented POST /api/v1/public/media/upload response body is not documented. The frontend tries three keys in order: data.path, data.file_path, data.relative_path.

    Action needed: Document the response shape and confirm the exact key name for the file path. 
    {
  "success": true,
  "data": {
    "path": "submission_files/ZrZEWkGzk5wfpiXtXhZLfZkW0B1uW7cHSoUFGZss.pdf",
    "url": "https://…/storage/submission_files/…",
    "size": 204800,
    "mime_type": "application/pdf"
  }
}
  • K
    Registration success response shape not documented Neither registration endpoint has a documented response shape. The frontend assumes { token: string, form?: IdeaForm } inside the data envelope.

    Action needed: Add saved response examples to the Postman collection. 
    {
  "success": true,
  "message": "Registration successful. Welcome to OTCI!",
  "data": {
    "token": "14|sometoken…",
    "user": { "id": 42, "first_name": "Ada", "last_name": "Okafor", "email": "ada@example.com", "user_type": "citizen" },
    "form": { "code": "EVT-2026-001", "title": "OTCI Innovation Challenge 2026", "fields": [ … ] }
  }
}

OTCI CMS — Remaining Gaps
Items still unintegrated after the latest sprint. Login, gallery CRUD, publish, section save, and admins are all wired — these are what remain.
⚠️
Current state: The CMS persists all page content to localStorage (store key otci-studio-v4) as a temporary measure. Gallery, admins, and login now use real API calls, but page content, charters, and activity log do not. Content is lost when browser storage is cleared.

4.1 Login — OTP / password UI mismatch

The CMS login screen displays a two-step OTP flow (email → 6 boxes labelled "digit 1–6") and shows the message "We sent a 6-digit code to your email." The backend only has POST /api/auth/login (email + password). The frontend now posts the joined digits as the password, which works but is confusing for users.

Option A (recommended): Implement OTP send/verify endpoints. This matches the existing UI exactly with no visual change needed.

POST/api/auth/send-codeStep 1 — sends 6-digit OTP to email
POST/api/auth/verify-codeStep 2 — verify code, return token

Option B: Update the UI copy so the second step is labelled "Enter your password" instead of "Enter the code". This requires a small JSX change but no new backend work.

ℹ️
After a successful login, the CMS continues to use GET /api/auth/me and POST /api/auth/logout.

4.2 Overview dashboard stats ✅ Resolved — v2.1

✅
Wired in this sprint. Overview.jsx now calls GET /api/admin/dashboard on mount and reads KPI counts from body.dashboard. See §2 for the exact response shape the frontend expects.

4.3 Pages list — load from API on mount

The Pages view lists all sections across all department pages. It reads entirely from the local store seeded at startup; it does not call GET /api/admin/pages to hydrate real content. Without this, edits made by other admins do not appear until the localStorage seed is manually cleared.

GET/api/admin/pagesList pages with status — hydrate S.pages on mount
GET/api/admin/pages/:slugFull page with sections — load when editor opens

The store's S.pages shape uses pid keys (home, about, ci, etc.) and each page has sections[].v for draft content and sections[].pub for published content. The API response must be mapped into this shape on load.

4.6 Editor — load page content from API

The Editor opens a page from the local store seed. It never calls GET /api/admin/pages/:slug to fetch the latest published or draft content. This means two admins editing the same page will overwrite each other.

When the editor mounts it should:

  1. Call GET /api/admin/pages/:slug to get the page and its sections.
  2. Map the response into the store shape, hydrating s.v (draft) and s.pub (published content).
  3. Update S.pages[pid] and re-render via commit().
GET/api/admin/pages/:slugLoad on Editor mount to hydrate S.pages[pid]
GET/api/admin/pages/:slug/sectionsSections list with draft + published content

The Department Admins screen lists all admins and allows inviting new ones. The list endpoint exists; the invite has two mismatches:

4.8 Missing CMS admin views — Feedback, Contact, Newsletter

The API layer (lib/api/index.js) already has fully-typed methods for three admin read flows, but no corresponding CMS views exist. The backend endpoints are assumed to follow the same { <resource>, meta } response format as other list endpoints.

Feedback submissions

GET/api/admin/feedbackPaginated list — response key expected: body.data[] (via standard list())
GET/api/admin/feedback/:idSingle feedback submission detail

The view should show: type (general / MDA), email (if provided), message, reference code, submitted date. Add a "mark read / archive" action if the backend supports status transitions.

Contact MCSD requests

GET/api/admin/contact-requestsPaginated list
GET/api/admin/contact-requests/:idSingle request detail

The view should show: name, email, phone, organisation, subject, message, reference code, submitted date.

Newsletter subscribers

GET/api/admin/newsletter/subscribersPaginated list of subscribers

The view should show: email, subscribed date, status (active / unsubscribed). An export-to-CSV action would be useful.

ℹ️
All three sets of API methods are already defined in adminFeedback, adminContact, and adminNewsletter in lib/api/index.js. No API changes are required — only new React views need to be built and wired into the sidebar navigation.

API Spec Inconsistencies
Contradictions and gaps found within the Postman collection itself, independent of the missing endpoints above. Each item has a concrete action needed.
  1. 1
    ⚠️ Pagination key — pagination vs. meta The collection overview documentation says paginated lists return a pagination key. Every saved response example uses meta (and links on submissions). The frontend currently accepts both keys.

    Action: Standardise on meta + links across all paginated endpoints. Remove the pagination key from all documentation.
  2. 2
    ⚠️ Accept invitation — two conflicting request body shapes POST /api/v1/public/invitations/accept appears twice with different bodies:
    • Public › Admin Invitations: { token, full_name, password, password_confirmation }
    • Admin › Admin Management: { token, first_name, last_name, password, password_confirmation }
    Action: Decide on one canonical body. The frontend uses first_name + last_name.
  3. 3
    ⚠️ Submissions URL prefix — no /api/v1 Every endpoint uses {{base_url}}/api/v1/…. All submission and submission-action routes use {{base_url}}/admin/submissions/… (no /api/v1).

    Action: Confirm whether the submissions routes intentionally skip the /api/v1 prefix. If not intentional, update to /api/v1/admin/submissions/….
  4. 4
    ❌ Admin login uses public login URL — no way to distinguish intent "Admin Login" in the collection uses POST /api/v1/public/auth/login, identical to public login. The CMS now uses POST /api/auth/login (a separate CMS auth namespace).

    Action: Confirm whether /api/auth/login is the canonical admin login URL and add it to the collection. Clarify the relationship between /api/v1/public/auth/login and /api/auth/login.
  5. 5
    ⚠️ Duplicate response fields in three endpoints
    • GET /admin/admins/stats: both pending_invites and pending_invitations carry the same value.
    • GET /admin/invitations/preview: both default_body and preview_body are identical strings.
    • GET /admin/submissions/stats: both by_status (rich objects) and status_counts (plain integers) carry the same data in different shapes.
    Action: Remove the duplicate field from each response.
  6. 6
    ⚠️ Date format inconsistency across responses Three different formats appear: ISO 8601, human-readable "May 10, 2026", and long-form human "Monday, 12 October 2026".

    Action: Standardise all machine-readable date fields on ISO 8601 UTC. If a human-readable string is needed for display, name it clearly (e.g. expires_at_label) alongside the ISO field.
  7. 7
    ❌ Missing response body documentation for the majority of endpoints The following endpoints have no saved example response in the Postman collection:
    • POST register/citizen
    • POST register/civil-servant
    • POST auth/login
    • GET auth/me
    • GET /public/sectors
    • GET /public/lgas
    • GET /public/mdas
    • GET /public/forms/current
    • POST /forms/{code}/submit
    • POST /media/upload
    • All message preview endpoints
    • GET /admin/submissions/{code}
    • All comment endpoints
    • Every single submission action
    • Every bulk submission action
    • GET /admin/profile
    • All Events/Fields/History endpoints
    • GET /admin/users
    Action: Add at least one saved success example and one error example (422 or 404) for each of the above.
  8. 8
    ⚠️ file missing from field type enum The spec for POST /admin/events/{code}/fields lists supported field_type values without file, yet the submit endpoint handles file-upload field answers.

    Action: Add file to the field_type enum for event fields.
  9. 9
    ⚠️ Single and batch invite share a URL with incompatible bodies POST /api/v1/admin/invitations serves both single ({ name, email, role }) and batch ({ emails[], role, … }) invites with completely different body shapes.

    Action: Either split into two distinct URLs (/invitations and /invitations/batch), or add a discriminator field (e.g. "mode": "single" | "batch").
